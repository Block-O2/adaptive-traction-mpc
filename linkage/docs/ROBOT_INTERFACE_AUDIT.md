# Laboratory Robot Interface Audit

## Audit status and scope

Audit date: 2026-07-30.

This was a read-only audit of the repository, local project folders, retained
configuration/URDF material, locally downloaded manuals and SDK archives, and
public ROKAE manufacturer documentation. No robot was connected, no command
was sent, no MATLAB plant or controller was modified, and no adapter or robot
dynamics model was implemented.

**Identity gate: not passed.** The available evidence does not establish the
laboratory manipulator's full commercial model, controller hardware, or
installed control-system/SDK version. Therefore this audit stops before
attributing any command, feedback, rate, or safety capability to the
laboratory robot. Generic xCore capabilities are recorded only as
model/version-dependent leads.

## Safety, watchdog, stops, collision, and limits

The actual laboratory safety configuration remains unresolved, including:

- configured safe joint/workspace/velocity/force limits;
- collision-detection thresholds and recovery behavior;
- protective-stop versus emergency-stop behavior exposed to the SDK;
- watchdog timeout and the motion taken after command loss;
- whether command discontinuities are rejected, ramped, clipped, or faulted;
- restart/reset sequence after communication loss, collision, or limit
  violation;
- external safety I/O wiring and enabling-mode requirements.

The official candidate manuals provide only conditional family-level facts:

- emergency stop has highest priority and requires manual release/reset;
- the `CR12-12/1.4` manual specifies STOP0 for the handheld emergency stop;
- Manual mode requires the three-position enabling switch and limits endpoint
  speed to 250 mm/s;
- Automatic mode permits programmed motion subject to the configured safety
  system;
- safety inputs/outputs and emergency stop must be tested before use.

These facts must not be treated as the installed laboratory configuration
until the model and controller are matched. Both candidate manuals also
exclude medical/life-critical use and require an application-specific risk
assessment. A rehabilitation research setup therefore requires explicit
laboratory safety review and manufacturer/integrator confirmation before any
human interaction; “collaborative robot” alone is not evidence of clinical
suitability.

## Required evidence to resume the audit

The minimum useful evidence package is:

1. Clear photograph of the manipulator nameplate, including the complete
   model suffix and serial number.
2. Photograph of the complete controller arrangement and controller/control
   cab nameplate. This must show whether the controller is built into the
   robot or is an MCC/other cabinet.
3. Teach Pendant screenshots of the electronic nameplate, controller model,
   xCore/HMI version, installed options, and authorization/license page.
4. The matching manufacturer hardware manual and xCore manual supplied with
   that unit.
5. The actual ROKAE SDK/RCI package, API reference, release notes, examples,
   supported OS/language matrix, and license/authorization information.
6. Network/fieldbus configuration and the documented command/feedback cycle,
   timestamp, watchdog, and communication-loss behavior.
7. Safety configuration export or integrator documentation covering stop
   categories, external safety I/O, collision thresholds, joint/workspace
   limits, and recovery.
8. Photographs and documentation for any flange/end-effector force/torque
   sensor, including model, location, calibration, coordinate frame, and
   sampling interface.

Until these items are available, implementing a controller adapter or choosing
an MPC action space would encode an unsupported interface assumption.
