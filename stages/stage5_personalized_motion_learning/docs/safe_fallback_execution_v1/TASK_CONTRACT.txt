==================================================
2. Architecture objective
==================================================

实现一种：

`Always-Ready Prevalidated Fallback`

正常路径保持：

current segment
→ continuous pass-through
→ next segment

异常路径变成：

current segment
→ prevalidated controlled deceleration
→ safe hold
→ fresh replan
→ resume

而不是：

current segment
→ endpoint
→ next plan not ready
→ abort

核心原则：

任何被允许进入pass-through执行的segment，都不能把未来安全性依赖于“下一次planner一定及时完成”。

==================================================
3. Compare fallback designs before coding
==================================================

至少比较以下实现思路：

A. Precomputed safe-stop branch

当当前segment建立/激活时，同时准备一个fallback braking suffix。
在某个预先确定的commit point：

- next primary ready + valid:
  continue primary/pass-through

- next primary not ready:
  atomically commit fallback suffix

fallback从commit时刻当前reference的
q/dq/ddq
开始，保持至少C2 continuity，并减速至零速安全hold。

B. Existing terminal-stop primitive reuse

若现有controller已经存在经过验证的stop/hold primitive，
评估能否预先绑定为当前segment的escape branch，而不是重新设计braking控制器。

C. 其他更小但语义等价的方案

允许提出，但不能依赖：
- endpoint之后才临时规划
- planner必须及时返回
- 放宽stale rule
- arbitrary sleep/wait

只选一个最小、安全、最容易证明的方案实现。

==================================================
4. Commit/deadline semantics
==================================================

fallback必须在endpoint之前有明确commit semantics。

不要使用拍脑袋固定毫秒数。

优先从：

- active trajectory
- current q/dq/ddq
- existing velocity/acceleration limits
- fallback braking duration
- certified feasible suffix

推导：

`latest safe fallback commit point`

到该点：

如果next plan未ready + valid，
立即永久commit fallback。

一旦fallback braking已经commit：

late-arriving primary plan不得中途抢占braking。

它必须：
- 被drop/defer
- 或等safe hold完成后重新基于fresh observation规划

这样避免：

brake → suddenly resume pass-through

造成新的不连续。

==================================================
5. Safety invariants
==================================================

不得修改：

- planner cost
- candidate search space
- task goal
- force threshold
- moment threshold
- clearance threshold
- ROM model / 125° assumption
- scorer-v2 semantics

- force/moment

正常情况下fallback不得影响当前smoothness。

`SAFE_FALLBACK_ARCHITECTURE_NOT_JUSTIFIED`

并停止。

==================================================
6. Failure handling after fallback
==================================================

fallback完成后进入明确的：

`SAFE_FALLBACK_HOLD`

此时：

- current trajectory已经零速结束
- robot/Human state继续正常观测
- late stale primary不得执行
- 必须使用fresh deployable observation重新请求plan
- 继续遵守100 ms rule

只有fresh plan完成并通过原validation后才允许resume。

Resume trajectory必须从当前hold状态连续开始。

记录：

- FALLBACK_COMMITTED
- FALLBACK_STOPPED
- FALLBACK_HOLD
- FRESH_REPLAN_REQUESTED
- RESUME_ACTIVATED

等明确事件。

预注册少量delay：
- 0 ms
- 100 ms
- 200 ms

execution仍不会出现
`PASS_THROUGH_PREFETCH_NOT_READY_AT_ENDPOINT`.

要求：

0 ms:
- 正常RSS pass-through
- smoothness不退化

100/200 ms:
- fallback在latest-safe-commit point前正确commit
- controlled deceleration
- safety PASS
- stale plan不激活
- safe hold
- fresh replan
- resume
- 最终任务COMPLETE

如果200 ms导致old plan超过100 ms：
应正确drop旧plan，
然后从hold状态做fresh replan；
不得为了完成任务绕过100 ms stale rule。
