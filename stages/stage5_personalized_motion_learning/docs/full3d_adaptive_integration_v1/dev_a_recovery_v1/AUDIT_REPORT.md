## Findings requiring attention

1. **High — fitted-model command continuity remains unproven and materially poor in some cases.** The C2 robot-cuff pose/twist bridge and q/dq/ddq reference continuity do not bridge the generalized action, allocated wrench or CR12 torque. In `regression_v2/balanced_near_upper_current_rom_r01/trace.npz`, adjacent *executed* recovery rows 1405→1406 are at 7.020→7.025 s, after 20 MuJoCo substeps, and change `population_prior_v1`→`belief_310`. Their q/dq/ddq reference and desired cuff pose/twist are identical, but the robot-site allocated force command changes by **49.581670 N**, allocated moment by **9.730 Nm**, and six-axis CR12 torque-command vector by **34.780445 Nm** in one 5 ms interval. The previous old-model command change from the last executed commissioning row at 7.015 s to the prior-model recovery row at 7.020 s was only **0.0909 N** force and **0.0581 Nm** torque. Across the 20 cases that activated the fitted model, first-command torque steps reach 34.780 Nm; the report's 2.208 Nm `balanced_ordinary_r01` example is not the maximum. These are adjacent-state comparisons, not a same-state old/new controller counterfactual, so the full step cannot be attributed solely to the model switch. The evidence does establish a model-activation-associated execution transient. **Required correction for any DEV-A handoff claim:** disclose the full range and avoid calling the physical command or wrench bumpless; test a concrete command-continuity mechanism in a separately versioned development change before claiming this issue closed. This finding does not establish a hard-limit violation: both cited rows record `TRACK`, first new torque components are inside the registered CR12 actuator bounds `[436, 436, 194, 102, 66, 66]` Nm, and that case records recovery measured-force peak 90.515 N, moment peak 7.416 Nm, positive deployable/true recovery clearance and zero recovery ROM violations. The repository has no demonstrated hardware torque-rate guarantee here.

2. **Medium — timeout wording should describe the actual stop condition.** Five `ACTIVE_RECOVERY_TIMEOUT` cases end at 9.055–9.075 s of the registered 10 s recovery budget. `runtime.py` rejects another plan when less than the inherited 1.5 s minimum segment fits (`now + minimum_duration > start + timeout`), before the wall clock reaches 10 s. This is a valid fail-closed decision under the configured segment rule, but “10 s timeout exhausted” would overstate elapsed execution. **Required wording:** “insufficient remaining 10 s budget for another minimum-duration segment.” The report's numerical durations are correct; the classification is not evidence that a shorter valid segment was tested.

3. **Low — checkpoint status is stale.** `dev_a_recovery_v1/STATUS.md` still says `regression_v2` is running and the report needs numeric completion, although all 24 final case artifacts and `regression_summary_v2.json` now exist. **Required correction:** mark it as a historical in-progress checkpoint or update its first paragraph to point to the completed final evidence. This is a documentation/provenance issue, not an outcome change.
